# Эксплуатация и восстановление без терминала

## Что означают статусы

| Статус | Значение | Что делать |
|---|---|---|
| `QUEUED` | Задание принято Queue | Обычно только подождать |
| `PROCESSING` | Идёт запрос к GetCourse | Подождать |
| `RETRY_SCHEDULED` | Временная ошибка, назначен повтор | Не запускать Allocate снова |
| `APPLIED` | GetCourse подтвердил запись кода | Всё в порядке |
| `DEAD` | Ошибка постоянная или повторы исчерпаны | Исправить причину и сделать Repair |

После ответа `ACCEPTED` запись может отсутствовать в D1 несколько секунд:
сначала она надёжно находится в outbox Durable Object, затем попадает в Queue.

## Быстрая ежедневная проверка

1. Откройте адрес `https://ВАШ_WORKER/health`.
2. Убедитесь, что `ok`, `database_ready`,
   `manager_configuration_ready`, `getcourse_configuration_ready` и
   `admin_token_ready` равны `true`.
3. Cloudflare → **Workers & Pages → gc-manager-round-robin → Metrics**:
   проверьте отсутствие резкого роста ошибок.
4. Cloudflare → **Queues → gc-manager-rr-write**: проверьте, что backlog не
   растёт постоянно.
5. Cloudflare → **D1 → gc-manager-round-robin → Console** и выполните:

   ```sql
   SELECT pool, status, COUNT(*) AS total
   FROM jobs
   GROUP BY pool, status
   ORDER BY pool, status;
   ```

Нормально, когда старые записи преимущественно `APPLIED`, а `PROCESSING` и
`RETRY_SCHEDULED` не накапливаются.

## Найти конкретного пользователя

В D1 Console вставьте ID пользователя:

```sql
SELECT job_id, mode, pool, user_id, manager_code, sequence_number,
       status, attempts, last_http_status, last_error_code,
       last_error_message, created_at, updated_at
FROM jobs
WHERE user_id = '516595363'
ORDER BY created_at DESC
LIMIT 20;
```

Запрос только читает данные. Email не нужен.

## Если пользователь остался `WAITING`

1. Подождите две минуты после первого `ACCEPTED`.
2. Если код не появился, подождите вторую проверку процесса ещё пять минут.
3. Найдите пользователя в D1.
4. Действуйте по результату:

   | Результат | Действие |
   |---|---|
   | `APPLIED` | не вызывать Allocate; повторно запустить только ветки проверки кода GetCourse |
   | `RETRY_SCHEDULED` | подождать автоматические повторы |
   | `DEAD` | исправить `last_error_message`, затем Repair |
   | строки ещё нет | проверить Queue и Real-time logs; не дублировать запрос до проверки |

5. Если Queue недоступна, задание остаётся в outbox. Alarm повторяет отправку
   с паузой от 30 секунд до 15 минут, Cron дополнительно будит каждый пул раз в
   пять минут.

## Repair без сдвига очереди

Сделайте временный блок **«Вызвать URL»** в GetCourse и ограничьте его одним
нужным пользователем. Тело:

```json
{
  "secret": "ВАШ_WEBHOOK_SECRET",
  "pool": "segment_1",
  "user_id": "{object.id}",
  "user_email": "{object.email}",
  "mode": "repair"
}
```

Worker найдёт ранее выбранный код в D1 или outbox и запишет именно его.
Round-robin не сдвинется.

Если это назначение старой системы и его нет в Cloudflare, после ручной
сверки можно передать код явно:

```json
{
  "secret": "ВАШ_WEBHOOK_SECRET",
  "pool": "segment_1",
  "user_id": "{object.id}",
  "user_email": "{object.email}",
  "mode": "repair",
  "manager_code": "s1_manager_4"
}
```

Нельзя исправлять такую карточку новым обычным `/v1/allocate`: он законно
выберет следующего менеджера и сдвинет круг.

## Посмотреть аварийно сохранённые сообщения

Аварийная Queue имеет consumer, который переносит сообщения в D1. Проверка:

```sql
SELECT received_at, job_id, pool, user_id, manager_code, error_code
FROM dead_letters
ORDER BY received_at DESC
LIMIT 100;
```

Даже если 24-часовой срок хранения сообщения Queue закончится, эта строка
остаётся в D1 до ручной очистки.

## Добавить, исключить или вернуть менеджера

Не редактируйте таблицу `managers` вручную. Источник истины — GitHub-файл
`src/manager-config.js`.

1. GitHub → конечный репозиторий → `src/manager-config.js`.
2. Нажмите карандаш.
3. Выполните нужное действие:
   - добавить строку в нужное место списка;
   - для временного исключения заменить `active: true` на `active: false`;
   - для возврата поставить `true`;
   - для изменения порядка переставить строки.
4. Увеличьте верхнее `version` на 1.
5. Перед добавлением нового `code` сначала создайте соответствующую ветку в
   GetCourse.
6. Commit в `main`.
7. Дождитесь зелёного Deploy и откройте `/health`.
8. В D1 Console снова сверяйте `managers`.

Менеджер получает только будущие назначения. Система намеренно не пытается
«догрузить» новичка до общего числа уже закреплённых клиентов.

Перед удалением кода менеджера или целого пула сначала дождитесь, чтобы:

- backlog очереди `gc-manager-rr-write` стал равен нулю;
- в D1 не осталось `PROCESSING` и `RETRY_SCHEDULED` для этого пула;
- все тестовые и рабочие карточки перестали быть `WAITING`.

До этого момента ветку соответствующего `manager_code` в GetCourse удалять
нельзя: старое, уже принятое задание может ещё находиться в outbox или Queue.
Для временного исключения менеджера безопаснее оставить его код в файле и
поставить `active: false`; тогда новые назначения его не получат, а старые
задания по-прежнему смогут завершиться.

## Добавить другой процесс

- Если второй процесс должен использовать тот же круг сегмента, передавайте в
  нём тот же `pool`, например `segment_1`.
- Если нужна полностью независимая очередь, добавьте новый пул в
  `src/manager-config.js`, например `process_2_segment_1`, увеличьте `version`
  и передавайте это имя из второго процесса.

Второй Worker и вторая D1 не нужны.

## Проверить строгую последовательность

В D1 Console:

```sql
SELECT sequence_number, user_id, manager_code, status, created_at
FROM jobs
WHERE pool = 'segment_1' AND mode = 'allocate'
ORDER BY sequence_number DESC
LIMIT 50;
```

Разверните строки от меньшего номера к большему. Коды должны повторять порядок
активных строк `src/manager-config.js`. Повтор номера запрещён уникальным
индексом D1.

## Реальные логи без терминала

Cloudflare → **Workers & Pages → gc-manager-round-robin → Logs → Live**.

Код не выводит webhook-secret, API-ключ или тело запроса. В ошибках Queue
используется `job_id`; email в публичном административном ответе маскируется.

## Что делать при неудачном GitHub Deploy

Не отключайте тесты и не меняйте рабочий GetCourse URL.

1. Откройте **Deployments → неудачная сборка → View build log**.
2. Исправьте файл в GitHub новым commit.
3. Дождитесь следующего зелёного Deploy.

Старая успешная версия продолжает работать, пока новая сборка не опубликована.

Если уже увеличили `manager-config version`, не делайте обычный rollback к
старому меньшему номеру: защита версий его остановит. Создайте новый commit на
основе нужного рабочего кода и поставьте версию конфигурации больше текущей.

## Безопасно отключить старый распределитель

После перевода GetCourse на Cloudflare старую схему держите выключенной, но не
удаляйте минимум семь дней. Перед окончательным удалением проверьте:

```sql
SELECT status, COUNT(*) AS total
FROM jobs
WHERE status <> 'APPLIED'
GROUP BY status;
```

Результат должен быть пустым либо содержать только уже разобранные вручную
`DEAD`. Дополнительно Queue backlog должен быть нулевым, а в
`dead_letters` не должно быть необработанных записей. Только после этого можно
удалять старые блоки и их ветки.

## Когда Free уже недостаточно

Переходите на Paid, если:

- назначений регулярно больше 2 500 в сутки;
- Queue показывает рост операций из-за частых retries;
- даже задержка до сброса суточного лимита неприемлема для бизнеса.

Пустой аккаунт даёт этому Worker весь бесплатный лимит, но не отменяет лимит
10 000 Queue operations/day.
