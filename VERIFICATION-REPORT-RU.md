# Отчёт проверки сборки v2.2.0

Дата проверки: 2026-09-21.

## Итог

Сборка прошла все доступные локальные проверки: 24/24 unit-теста и 13/13
интеграционных тестов в официальном Cloudflare Workers Vitest runtime. Ошибок
синтаксиса, D1-миграций или Wrangler bundle не обнаружено.

Это подтверждает внутреннюю логику и восстановление после смоделированных
сбоев. Реальное соответствие API-ключа, поля и веток конкретной школы можно
подтвердить только безопасным приёмочным тестом после Deploy.

## Unit-тесты — 24/24

Проверено:

- точное циклическое распределение;
- 10 003 и 250 003 последовательных назначения;
- итоговая разница между менеджерами не больше одного;
- независимость четырёх пулов при 100 000 перемешанных назначений;
- исключение и добавление менеджера;
- корректный переход к следующему активному менеджеру, если последний стал
  неактивным;
- Repair без сдвига курсора;
- валидация pool, user ID, email и manager code;
- запрет повторных пулов, кодов и пула без активного менеджера;
- запрет неизвестного стартового кода очереди;
- детерминированный hash конфигурации;
- ответы GetCourse: успех, 408, 425, 429, 5xx, неверный JSON и постоянные
  4xx/API-ошибки;
- ограниченная экспоненциальная шкала повторов;
- UTF-8/base64 для тела Import API.
- порядок первой установки: сначала `wrangler deploy` для provisioning, затем
  D1 migrations;
- ограниченные повторы временной ошибки миграции;
- остановка после трёх неуспешных попыток без бесконечного цикла;
- запрет запуска миграции, если первый provisioning/deploy завершился ошибкой.

## Интеграционные тесты Cloudflare — 13/13

Тесты выполнялись с настоящими локальными реализациями D1, SQLite Durable
Object, Queue event API и Worker runtime.

Проверено:

1. D1-миграции и автоматическая синхронизация четырёх пулов/20 менеджеров.
2. Отклонение неверного webhook-secret и некорректных входных данных.
3. Сто параллельных cold-start проверок синхронизируют конфигурацию без
   дублей и частично записанных данных.
4. Изменение manager-config без увеличения версии блокируется до исправления.
5. **1 000 одновременных HTTP-заявок в один пул**:
   - 1 000 ответов приняты;
   - 1 000 уникальных `job_id`;
   - последовательность ровно `1…1000`, без потерь и повторов;
   - распределение по пяти менеджерам ровно `200/200/200/200/200`.
6. Сохранение round-robin state после уничтожения и повторного создания
   экземпляра Durable Object.
7. Repair не меняет sequence и следующего менеджера.
8. Сбой отправки в Queue: outbox сохраняет запись; после восстановления
   отправляет один раз и только затем удаляет.
9. Успешная запись GetCourse и повторная доставка одного job: внешний API
   вызывается один раз, второй delivery только подтверждается.
10. 250 Queue-заданий обработаны пакетами по 10: все 250 подтверждены, все 250
    стали `APPLIED` с первой попытки, пропущенных записей нет.
11. Временный HTTP 503: `RETRY_SCHEDULED`, попытка учтена, сообщение получает
   delayed retry.
12. Постоянное отклонение GetCourse: статус `DEAD`, без бесконечных повторов.
13. Автоматически исчерпанное сообщение DLQ сохраняется в таблице
    `dead_letters`, а исходный job получает `DEAD`.

- `0001_initial.sql`: применена успешно.
- `0002_dead_letters.sql`: применена успешно.
- Таблицы `configuration_state`, `managers`, `pool_settings`, `jobs`,
  `legacy_assignments`, `dead_letters`: созданы.
- `wrangler 4.135.0 deploy --dry-run`: успешно.
- Bundle: 46.89 KiB, gzip 10.66 KiB.
- Wrangler распознал D1, Durable Object, обе Queue и обычные переменные.
- Конфигурация шаблона и синтаксис трёх исходных JS-файлов: успешно.
- D1 binding без `database_id` проходит проверку и распознаётся Wrangler как

- Воспроизведённая ранее ошибка Cloudflare API `7404` устранена: нулевой UUID

Фактическое создание ресурсов через API происходит только в Cloudflare-аккаунте
во время первого Deploy. Локальные тесты не используют чужой аккаунт и не могут
подменить этот последний приёмочный шаг; формат конфигурации соответствует
официальному механизму automatic provisioning Wrangler.

## Защита от перегрузки и зависания

- GetCourse ждёт только быстрое сохранение в Durable Object, а не свой же
  медленный Import API.
- Каждая позиция и outbox фиксируются в одной синхронной SQLite-транзакции.
- Queue consumer имеет `max_concurrency = 1`: запросы записи в GetCourse не
  создают неконтролируемый параллельный шторм.
- Рабочий batch не больше 10 сообщений; обработка последовательная.
- Временные ошибки получают экспоненциальные задержки до часа.
- Ошибка отправки outbox в Queue получает паузу от 30 секунд до 15 минут.
- Проверка manager-config кешируется на 60 секунд, а `/health` на 30 секунд,
  чтобы лишние обращения не расходовали D1 Free.
- Тело публичного webhook читается потоком и жёстко ограничено 12 KB.
- Повторная доставка одного Queue job идемпотентна.
- После исчерпания попыток payload сохраняется в D1 через отдельный DLQ
  consumer.
- При исчерпании бесплатного суточного Queue-лимита неотправленная запись
  остаётся в Durable Object outbox; она не превращается в новый manager code.

## Что ещё обязательно проверить после Deploy

- реальный `GC_API_KEY` вашей школы;
- точное техническое имя дополнительного поля `manager_code`;
- соответствие каждого кода ветке назначения менеджера;
- один пользователь, полный круг и параллельный тест GetCourse;
- фактическое время Cloudflare → GetCourse;
- что ответ `ACCEPTED` не сохраняется в пользовательское поле.

Ни одна автоматическая проверка не может гарантировать доступность внешнего
GetCourse API или исключить ошибку в настройках его процесса. Поэтому
`WAITING`, две отложенные проверки и уведомление администратора остаются
обязательными.
