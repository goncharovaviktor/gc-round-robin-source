# Настройка процесса GetCourse

## Общая последовательность блока

Для каждого сегмента используйте одну и ту же структуру:

1. Изменить дополнительное поле пользователя: `manager_code = WAITING`.
2. Вызвать URL Worker.
3. Подождать 2 минуты.
4. Проверить короткие коды и назначить соответствующего персонального
   менеджера.
5. Если поле всё ещё `WAITING`, подождать ещё 5 минут и проверить повторно.
6. Если после второй проверки поле осталось `WAITING`, уведомить
   администратора и остановить эту ветку. Не делать новый вызов Allocate.

Скрипт намеренно не проверяет, был ли уже назначен персональный менеджер.
Штатная операция GetCourse в ветке кода переназначит его.

## Блок «Вызвать URL»

Для первого сегмента:

- метод: `POST`;
- URL:

  ```text
  https://ВАШ_WORKER/v1/allocate
  ```

- тип тела: JSON;
- тело:

  ```json
  {
    "secret": "ВАШ_WEBHOOK_SECRET",
    "pool": "segment_1",
    "user_id": "{object.id}",
    "user_email": "{object.email}"
  }
  ```

Для остальных сегментов меняется только `pool`: `segment_2`, `segment_3`,
`segment_4`.

`run_key` добавлять не нужно и нельзя. Сведения о текущем персональном
менеджере передавать тоже не нужно.

## Самая важная настройка

Поле GetCourse **«Записать результат/ответ в дополнительное поле»** должно
быть пустым или отключено.

Worker отвечает коротким словом:

```text
ACCEPTED
```

Это только подтверждение приёма. Сам Worker позже запишет код вида
`s1_manager_2` через Import API. Если сохранить ответ блока, GetCourse запишет
`ACCEPTED` поверх нужного поля и логика сломается так же, как ранее с `OK` и
`WAITING`.

## Ветки назначения

Пример для `segment_1`:

| Условие | Действие |
|---|---|
| `manager_code = s1_manager_1` | Назначить менеджера 1 |
| `manager_code = s1_manager_2` | Назначить менеджера 2 |
| `manager_code = s1_manager_3` | Назначить менеджера 3 |
| `manager_code = s1_manager_4` | Назначить менеджера 4 |
| `manager_code = s1_manager_5` | Назначить менеджера 5 |
| `manager_code = WAITING` | Задержка 5 минут и повторная проверка |

После второй проверки `WAITING` создайте уведомление ответственному сотруднику
с ID пользователя и названием сегмента. Не назначайте случайного менеджера и
не запускайте Allocate повторно.

## Несколько процессов и сегментов

- Два процесса с одинаковым `pool` используют одну общую последовательность.
- Для независимой последовательности создайте новый `pool`, например
  `process_2_segment_1`, добавьте его менеджеров в `src/manager-config.js`,
  увеличьте `version` и сделайте отдельные коды веток.
- Все сегменты можно запускать параллельно: Durable Object каждого `pool`
  независим, а запросы внутри одного `pool` выполняются по одному.

## Временный блок Repair

Для карточки, уже принятой новой системой, но оставшейся `WAITING`, можно
использовать:

```json
{
  "secret": "ВАШ_WEBHOOK_SECRET",
  "pool": "segment_1",
  "user_id": "{object.id}",
  "user_email": "{object.email}",
  "mode": "repair"
}
```

Repair ищет прежний код в D1 или ещё не отправленном outbox и повторяет его.
Позиция round-robin не меняется.

Для записи старой системы, которой нет в Cloudflare, укажите проверенный код
явно:

```json
{
  "secret": "ВАШ_WEBHOOK_SECRET",
  "pool": "segment_1",
  "user_id": "{object.id}",
  "user_email": "{object.email}",
  "mode": "repair",
  "manager_code": "s1_manager_4"
}
```

Указанный код должен существовать в таблице `managers`; он может быть
неактивным. Явный Repair используйте только после сверки старой таблицы.
