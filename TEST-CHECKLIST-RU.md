# Приёмочный тест перед рабочим запуском

## A. Проверка Deploy

- [ ] В Cloudflare последний Deployment зелёный.
- [ ] В build log прошли 20 unit- и 13 интеграционных тестов.
- [ ] Миграции `0001_initial.sql` и `0002_dead_letters.sql` применились.
- [ ] `/health` возвращает HTTP 200, `ok: true`, версию `2.1.0`.
- [ ] В `/health` все четыре признака готовности равны `true`.
- [ ] Количество пулов и активных менеджеров правильное.
- [ ] В Bindings видны `RR_DB`, `POOL_ALLOCATOR`, `GC_WRITE_QUEUE`,
  `GC_WRITE_DLQ`.
- [ ] У рабочей Queue `Max concurrency = 1`.
- [ ] В GitHub нет настоящих API-ключей и секретов.
- [ ] Ответ блока URL нигде не записывается в `manager_code`.

## B. Сверка менеджеров

Cloudflare → D1 → `gc-manager-round-robin` → Console:

```sql
SELECT pool, manager_code, manager_name, active, sort_order
FROM managers
ORDER BY pool, sort_order;
```

- [ ] Каждый `pool` существует.
- [ ] Каждый `manager_code` совпадает с веткой GetCourse посимвольно.
- [ ] Порядок строк правильный.
- [ ] В каждом пуле есть хотя бы один активный менеджер.
- [ ] Нет тестовых или лишних кодов.

## C. Один тестовый пользователь

1. Запустите копию процесса только для одного тестового пользователя.
2. Сразу после первого блока поле должно стать `WAITING`.
3. Блок URL должен быстро получить `ACCEPTED`, без 10-секундного timeout.
4. В течение двух минут поле должно получить короткий код менеджера.
5. Ветка GetCourse должна назначить нужного персонального менеджера.
6. В D1 Console выполните:

   ```sql
   SELECT pool, sequence_number, user_id, manager_code, status,
          attempts, last_error_message
   FROM jobs
   ORDER BY created_at DESC
   LIMIT 5;
   ```

7. Ожидается `status = APPLIED`, `attempts = 1`, ошибка пустая.

## D. Полный круг

Создайте тестовых пользователей: число менеджеров плюс два. При пяти
менеджерах — семь пользователей.

- [ ] Первые пять получили все пять кодов по одному разу.
- [ ] Шестой получил тот же код, что первый.
- [ ] Седьмой получил тот же код, что второй.
- [ ] `sequence_number` идёт подряд без повторов.
- [ ] Никто не остался `WAITING`.

## E. Параллельный тест двух сегментов

Запустите близко по времени по 15 тестовых пользователей в двух сегментах.

- [ ] Все блоки URL получили `ACCEPTED`.
- [ ] Нет HTTP timeout GetCourse.
- [ ] В каждом сегменте разница между менеджерами не больше одного.
- [ ] Последовательности двух сегментов независимы.
- [ ] Нет `DEAD` и долго висящих `RETRY_SCHEDULED`.

Проверка в D1 Console:

```sql
SELECT pool, manager_code, COUNT(*) AS total
FROM jobs
WHERE mode = 'allocate' AND status = 'APPLIED'
GROUP BY pool, manager_code
ORDER BY pool, manager_code;
```

## F. Repair

1. Возьмите тестового пользователя с успешным назначением.
2. Выполните временный GetCourse-блок `mode: repair` из
   `OPERATIONS-AND-RECOVERY-RU.md`.
3. Убедитесь, что появилась новая строка `mode = repair` с тем же кодом.
4. Запустите следующего обычного пользователя.
5. Проверьте, что круг продолжился так, будто Repair не выполнялся.

## G. Контроль очереди и аварийного хранения

Через Cloudflare Dashboard:

- [ ] `gc-manager-rr-write` после тестов возвращается к нулевому backlog.
- [ ] `gc-manager-rr-dlq` не накапливает сообщения.
- [ ] Таблица `dead_letters` пуста:

  ```sql
  SELECT COUNT(*) AS total FROM dead_letters;
  ```

Не создавайте искусственную ошибку GetCourse на рабочем API-ключе. Сбои,
retries, outbox и DLQ уже проверены автоматическими интеграционными тестами.

## H. Допуск к рабочему запуску

Переключать основной процесс можно только если:

- Deploy, один пользователь, полный круг и параллельный тест успешны;
- Worker отвечает `ACCEPTED` заметно быстрее лимита GetCourse;
- нет `DEAD` и растущего Queue backlog;
- в GetCourse есть две проверки `WAITING` и уведомление администратору;
- старые Apps Script и таблица сохранены;
- обычная ветка ошибки не вызывает `/v1/allocate` повторно.

После переключения вручную контролируйте первые 30 рабочих назначений. Старый
Apps Script отключите, но не удаляйте минимум семь дней.
